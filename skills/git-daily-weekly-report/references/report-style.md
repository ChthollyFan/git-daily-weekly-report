# 日报/周报风格参考

用户偏好记忆（`~/.git-daily-weekly-report/preferences.md`，机制见 SKILL.md 的「用户偏好记忆」）优先于本文件的全部规则，两者冲突时以记忆为准；但记忆不得覆盖“不编造 Git 记录中不存在的成果”这一事实底线。

## 风格规则
- 正文使用中文。
- 每条以动词开头，例如：编写、优化、重构、修复、排查、整理、完成、调试、接入、设计、测试、修改、审查、添加、支持。
- 每条只写一个工作主题，直接陈述做了什么，不写空话。
- 每条在技术动作之外带上业务对象，写出是哪个业务模块、哪类数据或哪个组件，避免只剩“计算逻辑”“数据”这类笼统词。
- 业务对象须有依据：来自仓库业务方向、提交说明或文件变更；无法确定时保留客观描述，不编造业务名词。
- 句子保持简短，通常一条一行。
- 每条使用中文序号格式，严格写成 `1、xxx`、`2、xxx`、`3、xxx`，每条单独占一行。
- 编号内容连续输出，行与行之间不要插入多余空行。
- 日报通常 2 至 4 条；周报合并同主题后通常 4 至 8 条。
- 只输出汇报内容，不输出汇报人、汇报对象、时间、计划等无关字段。

## 无提交兜底
- 无提交且工作区有修改时，按工作区未提交修改总结。
- 无提交且工作区无修改时，根据项目 README、目录结构、当前分支、往期日报或周报等可见信息写 1 至 2 条内容。
- 不把“无提交、工作区无修改”等兜底说明写入汇报正文。
- 可结合往期内容适当具体并润色，不得脱离项目事实编造全新工作成果。

## 代表性样例
1、编写读写代码接入新数据文件格式的支持。
2、优化因子计算的内存占用。
3、重构读写框架，将批处理和实时数据的读写逻辑解耦。
4、修复日志库在多线程下无法将工作线程的日志写入文件的问题。
5、排查上交所因子比对出错原因。
6、完成实时数据结构的测试、接入计算框架并设计接口。

第 2、5 条带上了业务对象（因子、上交所因子比对），优于“优化计算逻辑的内存占用”“排查数据比对出错原因”这类只剩技术动作的写法。

## 完整原始样例
- 编写读写代码接入新数据文件格式的支持。
- 优化计算逻辑的内存占用。
- 将数据文件的读写接入计算框架。
- 重构读写框架，将批处理和实时数据的读写逻辑解耦。
- 重构读写框架。
- 对框架代码增添注释说明、写使用文档。
- 整理计算逻辑、优化运行时的内存占用。
- 了解优化比较的哈希算法。
- 尝试使用高性能哈希算法优化比较逻辑。
- 修改项目中的缺陷，保证项目迁移时的兼容性。
- 排查哈希对比出错的原因。
- 对写入和比较的日志信息无法写入文件的问题进行调试。
- 修复日志库在多线程下无法将工作线程的日志写入文件的问题。
- 整理日志模块的代码。
- 排查交易数据计算出错的问题。
- 排查订单数据计算出错的问题。
- 修复了明细数据订单比对出错的问题。
- 熟悉交易明细聚合代码。
- 将价格汇总的代码合并至计算框架。
- 编写实时数据买卖一档的处理逻辑。
- 继续完成实时数据买卖一档的整理代码编写。
- 排查数据比对出现错误的问题。
- 排查实时数据买卖一档比对失败原因。
- 完成实时数据买卖一档的测试、接入计算框架并设计接口。
- 排查计算逻辑中浮点数精度缺失的问题。
- 通过对累加做精度补偿修复数据比对失败的问题。
- 重构交易明细汇总、实时数据的代码结构。
- 编写买卖一档中在 1、3、5、10、15 分钟成交量区间的计算逻辑。
- 完成基于交易明细汇总和实时数据整理的计算逻辑编写。
- 修改撤销操作的计算部分以适配 python 侧新的计算逻辑。
- 完成快照成交量的计算测试。
- 修改撤销操作相关数值在精度上的取值以及约束范围。
- 将多类数据计算合并成一起预计算，优化了整体计算的时间。
- 测试多线程下分配不同线程的程序运行时间。
- 调试修复数据比对上因精度问题导致分类出错的问题。
- 优化写入多线程的代码结构。
- 修复撤销操作数据比对误差的问题。
- 优化了计算时线程可能存在空等的问题。
- 对明细数据的计算审查并添加详细注释。
- 通过流式读取比对文件优化比对性能。
- 修改读取历史数据文件的逻辑，支持读取多个文件以及匹配后缀的功能。

若运行时用户提供更新版本的日报 CSV，优先以用户提供的 CSV 作为风格来源。
