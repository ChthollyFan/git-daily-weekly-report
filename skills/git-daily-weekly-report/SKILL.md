# Git 日报/周报总结

## 目标
把指定 Git 仓库、指定日期范围内的提交记录，转换为用户可直接使用的日报或周报正文。正文一律中文，风格参考 `references/report-style.md`。

## 输入
- `repo`：Git 仓库路径。若未提供，当前工作目录是 Git 仓库则使用当前目录，否则先向用户询问。
- `type`：`daily` 或 `weekly`，默认 `daily`。
- `date`：日期，支持 `YYYYMMDD` 或 `YYYY-MM-DD`。日报默认今天；周报默认今天，作为范围结束日。
- `days`：周报最多回溯天数上限，默认 `7`。周报起点为从 `date` 回溯到的最近一个星期一，并受该上限约束，范围为起点到 `date`（含结束日当天）。

## 用户偏好记忆
用户对汇报的内容、格式、风格提出的不满、纠正或建议，都记入记忆文件；此后生成汇报时按第一优先级遵守，与 `references/report-style.md` 或本文件的规则冲突时以记忆为准。

- 记忆文件位于当前用户主目录下：`~/.git-daily-weekly-report/preferences.md`，Windows 下形如 `C:\Users\<用户名>\.git-daily-weekly-report\preferences.md`。文件不存在即视为还没有记忆。
- 读取：每次生成汇报前读取该文件，把其中仍生效的条目作为本次输出的最高优先级约束。
- 记录：用户对已生成的汇报表达不满、要求改写或提出风格建议时，先按要求把汇报改到满意，再把该偏好追加进记忆文件，并简短告知用户已记录。
- 条目格式：`- [类别] 偏好内容（来源：YYYY-MM-DD）`，类别取 `内容`、`格式`、`风格` 之一；同一偏好再次出现时不重复记录，改为更新来源日期。
- 冲突处理：新旧条目矛盾时保留新的、删除旧的；用户明确撤销某条偏好时删除该条。
- 只记录用户对汇报内容、格式、风格本身的偏好，不记录被分析仓库的业务事实。记忆文件所在路径不在当前可写范围时，向用户说明并请求授权后再写。
- 事实底线不受记忆覆盖：无提交且工作区无改动时，仍不得编造 Git 记录中不存在的成果；用户要求写满条数时按可见信息尽力具体，仍不足以支撑时说明原因。

## 执行步骤
1. 读取用户偏好记忆（路径见「用户偏好记忆」），把其中仍生效的条目作为本次输出的最高优先级约束；文件不存在时按无记忆处理。
2. 校验仓库：执行 `git -C <repo> rev-parse --is-inside-work-tree`，失败时向用户确认正确仓库路径。
3. 解析日期范围：
   - 日报：仅取 `date` 当天。
   - 周报：从 `date` 回溯到最近一个星期一（`date` 本身是星期一时即当天），起始日不早于 `date-(days-1)`，范围取 `[起始日, date]`。
4. 推测仓库的业务方向，形成撰写汇报用的业务画像，只作内部上下文，不写入最终输出：
   - 读取仓库 README、目录结构、顶层模块名、依赖与构建清单（如 `package.json`、`CMakeLists.txt`、`requirements.txt`）、主要源码文件的命名，辨别该仓库做的是哪些业务方向。
   - 结合日期范围内的提交历史，归纳业务方向与关键业务对象，例如业务模块、数据类型、数据源、外部组件。
   - 仓库可见信息不足以判断业务方向时，不臆造业务领域，退回第 8 步的兜底规则。
5. 运行脚本获取提交。脚本位于本技能目录下的 `scripts/fetch_git_commits.py`，其中“技能目录”指本 SKILL.md 文件所在目录，请拼成绝对路径后执行：
   - 日报：`python "<技能目录>/scripts/fetch_git_commits.py" --repo <repo> --type daily --date 20260814`
   - 周报：`python "<技能目录>/scripts/fetch_git_commits.py" --repo <repo> --type weekly --date 20260814 --days 7`
6. 脚本返回 JSON，包含 `commits` 和 `worktree`。
7. 如果 `commits` 不为空：
   - 对每笔提交，先看 `subject` 和 `files`；信息不足时运行 `git -C <repo> show --stat --oneline <hash>` 补充变更上下文。
   - 合并同一主题的多笔提交，结合业务画像按日报风格生成总结。
8. 如果 `commits` 为空：
   - 查看 `worktree.changed_files`。工作区有修改时，运行 `git -C <repo> diff --stat`、`git -C <repo> diff --cached --stat`、`git -C <repo> status --porcelain`，结合文件内容按未提交修改总结。
   - 工作区也没有修改时，查看项目 README、目录结构、当前分支、往期日报或周报、最近修改或打开的文档，结合项目情况和往期内容撰写 1 至 2 条内容，可适当具体并润色。
   - 项目可见信息也不足时，不生成汇报正文，向用户说明暂无可用改动内容，请用户补充，不虚构具体成果。
9. 读取 `references/report-style.md`，结合用户偏好记忆，按用户日报风格生成最终汇报内容。
10. 用户对结果表达不满、要求改写或提出建议时，先按要求改到满意，再按「用户偏好记忆」的条目格式把该偏好写入记忆文件，并简短告知已记录。

## 输出要求
- 只输出汇报内容，即“今日工作总结”或“本周工作总结”的分点正文。
- 不输出汇报时间、汇报人、汇报对象、计划、其他事项、附件、评论等字段。
- 日报内容用“今日工作总结”作为标题，周报内容用“本周工作总结”作为标题，标题后逐条输出。
- 每条必须使用中文序号格式，严格写成 `1、xxx`、`2、xxx`、`3、xxx`，每条单独占一行。
- 编号内容连续输出，行与行之间不要插入多余空行。
- 不使用 Markdown 无序列表、阿拉伯数字加句点、括号编号或其他编号格式。

## 写作规则
- 每条以动词开头，例如：编写、优化、重构、修复、排查、整理、完成、调试、接入、设计、测试、修改、审查、添加、支持。
- 每条只写一个主题，句子简短。日报通常 2 至 4 条，周报通常 4 至 8 条。
- 每条在技术动作之外带上业务对象，例如业务模块、数据类型、数据源或组件，避免只写“计算逻辑”“数据”这类笼统词；业务对象优先取自业务画像，其次是提交说明与文件变更，无法确定时保留客观描述，不编造业务名词。
- 汇报正文示例：
  1、优化因子计算的内存占用。
  2、排查上交所因子比对出错原因。
  确实无法确定业务对象时，才退回笼统写法，例如“优化计算逻辑的内存占用。”
- 只依据指定日期范围内的提交说明和文件变更，不补充 Git 记录中不存在的计划、结果或实现细节。
- 同一功能的多笔提交合并为一条，不逐笔罗列无信息量的 commit message。
- 无提交且无工作区修改时，结合项目现状与往期日报或周报内容撰写 1 至 2 条内容，可适当具体并润色。
- 不得脱离项目事实编造全新工作成果，可基于往期内容合理扩展。
- 无提交、无工作区修改等兜底说明不要写入汇报正文。
